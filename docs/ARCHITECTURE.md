# Архитектура БлокСкан

Нативное приложение: Kotlin, Jetpack Compose, Material 3, MVVM, Coroutines/Flow. Один модуль `app`, пакет `ru.blockscan.app`.
Бизнес-логика (`core`, `domain`) не зависит от Android и целиком покрыта JVM-тестами.

```
core/      чистая логика без Android: IP/CIDR/калькулятор/планировщик диапазонов, SSE-парсер
domain/    модели, парсеры ответов, вердикты, лимитер, IpChecker (цикл проверки), ScanEngine (очередь), интерфейсы хранилищ
data/      OkHttp-клиент (HttpCheckApi), SQLite (SqliteStore), SharedPreferences (SettingsStore), экспорт
service/   ScanService: foreground-уведомление и кнопки Пауза/Продолжить/Стоп
ui/        Compose-экраны, навигация, ViewModel'и, тема
```

## Поток данных одной проверки (IpChecker)

```
 ввод IP ─► /api/v1/check ─► CheckParser ─► статика (StaticResult) ─┐
            (повторы при 5xx/сети,                                   │ id
             интервал между запросами)                               ▼
                                              StartLimiter.acquire() (≤ N запусков/мин, общий)
                                                                     ▼
                                      /api/v1/probe/{id} (SSE) ─► started → result×N → done
                                                                     ▼
                       CheckRecord обновляется на каждом событии; DONE только по событию done
```

Единица хранения — `CheckRecord`: **только исходные ответы** (`staticRaw`, `probeRaw`) и метки времени. Всё остальное (статусы, итог, вердикты) вычисляется из них
(`overall()`, `summary()`), поэтому оригиналы всегда доступны для диагностики и экспорта, а логику можно менять без миграции данных.

### Модель состояний
Две независимые оси, чтобы не смешивать разные вещи:
- статика: `PENDING / LISTED / NOT_LISTED / UNKNOWN / ERROR`;
- динамика: `NOT_REQUESTED / UNAVAILABLE / QUEUED / RUNNING / PARTIAL / DONE / FAILED`.

Итог `Overall` (7 состояний из ТЗ) считается из пары осей. Правило безопасности: `COMPLETE` возможен только при `dyn == DONE`; «нет в списках» без динамики даёт `NOT_LISTED`, а не «чисто».

### Ожидание сканеров
Нет фиксированных пауз: идёт чтение SSE до события `done`. Предохранитель — `withTimeout(probeTimeoutSec)`. Исходы:
`done` → DONE; обрыв/таймаут при ≥1 результате → PARTIAL (результаты сохраняются); без результатов → повтор, затем FAILED; 429 → ожидание и повтор.
Повторная динамика для того же IP не запускается, пока идёт предыдущая: один IP обрабатывает один воркер.

## Массовое сканирование (ScanEngine)

- Подсеть разворачивается лениво (`ScanPlanner`, `BigInteger`, предел 65 536 адресов) и пишется в таблицу `scan_items` одной транзакцией со статусом `QUEUED`.
- Воркеры (1…3, по умолчанию 1) атомарно берут следующий `QUEUED` адрес (`claimNext`), проверяют его `IpChecker`, сохраняют результат. Лимит запусков сканеров и интервал между `/check` общие для всех воркеров.
- Пауза мягкая (текущие проверки доводятся до конца), остановка жёсткая (отмена корутин, адреса возвращаются в очередь, задание закрывается).
- Прогресс пишется в БД на каждое изменение (промежуточные обновления троттлятся до 2 в секунду на адрес), ETA считается по скользящему окну последних завершений и показывается после 4 завершённых адресов.
- Восстановление: при старте процесса `recoverInterrupted()` переводит `RUNNING`-задание в `PAUSED` и возвращает адреса `RUNNING → QUEUED`; завершённые не пересчитываются. Продолжение по кнопке.
- Один сбойный адрес не останавливает очередь: он завершается состоянием «Ошибка проверки».

## Фоновая работа
`ScanService` (foreground, тип `dataSync`) держит процесс и показывает уведомление с прогрессом и кнопками. Движок живёт в `AppContainer` (процесс), а не в Activity, поэтому поворот экрана и сворачивание ничего не прерывают.
Служба возвращает `START_NOT_STICKY`: после убийства процесса автозапуск из фона запрещён ограничениями Android, продолжение выполняется вручную (данные сохранены).
Разрешение `POST_NOTIFICATIONS` запрашивается перед запуском; без него сервис работает, но уведомление скрыто системой.

## Отклонения от ТЗ (с причинами)
| ТЗ | Сделано | Причина |
|---|---|---|
| Room | `SQLiteOpenHelper` | Процессор аннотаций Room при сборке грузит нативную sqlite-jdbc, ненадёжную в JVM под Termux; сборка на телефоне важнее |
| Retrofit/Ktor | OkHttp + kotlinx.serialization (дерево JSON) | Нужен потоковый SSE и терпимый к неизвестным полям разбор; Retrofit тут не даёт выигрыша |
| WorkManager | Foreground Service | Задача долгая, интерактивная, с паузой; WorkManager для этого не подходит |
| compileSdk 35 | compileSdk/targetSdk 34 | aapt2 из пакета Termux корректно работает с android.jar 34 |
| Примеры 192.168.x в ТЗ | Для частных адресов динамика пропускается (настройка) | По данным сторонних клиентов сервис не запускает для них сканеры; не проверено, поэтому отключаемо |

## Тесты (`app/src/test`)
Фикстуры сняты с реального сервиса. Покрыто: парсинг и неизвестные поля, IPv4/IPv6/CIDR, планировщик, SSE-парсер, вердикты на реальном потоке (37 сканеров), лимитер, таймауты и повторы,
частичные результаты, очередь, пауза/стоп/восстановление, HTTP+SSE через локальный сервер, экспорт. `LiveApiTest` ходит на реальный cheburcheck.ru только при `CHEBURCHECK_LIVE=1`.
